# DL3DV 控制相机核查（2026-09-18）

用户指出生成视角与 GT 不一致、后期崩坏后，对已有五场景相机和本地适配器进行核查。本次没有重跑 GPU 推理，也没有修改历史相机、视频或分数。

## 论文要求与本地实现

[WorldWarp 补充材料 §7](https://arxiv.org/html/2512.19678v1#S7) 说明先用 TTT3R 从参考视频估计相机内外参。因而本地使用参考视频估计轨迹有论文依据，但这不意味着允许把任意不同视角当成正确生成结果；新视角合成目标仍是给定参考轨迹对应的画面。

本地 `scripts/worldwarp_benchmark.py` 的 `calibrate` 保存逐帧原始预测 K；`generate` 直接读入。与[上游 pose_control.py](https://github.com/HyoKong/WorldWarp/blob/main/pose_control.py) 的参考视频入口不同：后者将主点设为画面中心，并对全部预测 K 取时间平均。本地漏掉了该处理。这是已经确认的实现差异，但尚未通过受控实算证明其贡献，不能声称补上平均就能修复全部问题。

## 保存相机的实际偏差

以下比较 `reference_ttt3r_cameras.npz` 与同运行中的 `dataset_cameras.npz`；各自转为相对首帧的 OpenCV c2w。旋转为逐帧旋转矩阵的测地角度，焦距比为相同 720×480 空间下 `fx_control / fx_dataset`。这些是**请求相机的偏差**，不是六项评分中的生成视频 DUSt3R R_dist。

| 建筑与雕像 | 0.56 | 8.62 | 1.254 | 1.253 |

焦距的系统偏差与遗漏时间平均是两件事：平均只能抑制逐帧变化，不能自动校正焦距与标定值的差异。不能把上表所有偏差归因于漏平均。本次未独立用图像对应点重新标定数据集相机，仍以保存的数据集标定为参照。

## 分段与尺度核查

根据实际调用的 `chunk_pose_bounds` 和 `run_inference_chunk` 的选帧逻辑，目标帧索引为 0–48、44–92、88–136、132–180、176–224。后四段去掉 5 个上下文帧后，交付恰为 0–224，未发现这一层的跳帧或错位。该检查验证代码中的请求帧映射，不证明生成图像真的服从相机。

原版每段重新用 TTT3R 估计历史深度和位姿，后续段将历史位姿替换为新估计值，未来运动仍来自参考相机。代码没有在这里显式拟合局部深度与参考平移的尺度对齐。是否发生足以造成崩坏的尺度漂移，仍需保存局部深度/相机并做重投影实算。TTT3R 与数据集平移单位本来可以不同，单纯比例不为 1 不是错误证据。

三项目和 F/G/H 复用同组参考相机，因此共享这项输入偏差；它们还各有几何尺度、历史生成误差等因素。低图像分数同时混合视角不匹配与图像生成质量，不能据此隔离评价模型或某个几何模块。

## 对旧报告的更正与后续验收要求

旧视频和指标保留为该本地配置的实际结果，数值计算完成不等于论文基线复现成功。撤回将“各批次核验通过”理解为相机对齐/质量验收通过的表述；暂不据这些排名确定哪个模块更好。

后续应先做单场景、单段验证：明确区分“恢复上游平均内参的 TTT3R 轨迹”与“数据集标定 K/位姿诊断”两种配置。后者需校准几何与相机平移单位，属于单独的诊断协议，不能直接称论文原版。保存源图重建、目标视角几何渲染、有效掩码、深度尺度和扩散结果，查清视角错误从哪一级开始，再扩大至五场景。尚未执行该重跑。
