# WorldCrafter：源码架构与本项目借鉴分析

分析日期：2026-09-22。依据：本地源码快照、仓库自带论文、官方仓库与论文网页。

**判断：它是你们“长期空间记忆与回访一致性”方向的重要对照，但不是单图直接生成完整 3DGS 资产的工具。** 最值得学习的是目标视角驱动的历史检索与记忆读取；最值得进一步研究的是历史可信度、生成误差纠正和真正增量式记忆。

- [来源与逐文件 SHA-256](../../../WorldCrafter/UPSTREAM_SNAPSHOT.json)记录了快照与验证结果；导出文件逐一与克隆内容核对相同。

论文：[WorldCrafter: Consistent Video World Model with Implicit 3D-aware Memory](https://arxiv.org/abs/2609.24984)；[本地 PDF](../../../WorldCrafter/assets/WorldCrafter.pdf)。

## 2. 它具体在做什么

输入一张图片或文本、相机运动及提示词，持续生成相机控制的视频。长期场景信息通过历史 latent 档案保存，每次根据将要观察的位置选择历史，再编码成适合当前目标视角的记忆。

公开主推理路径没有 TTT3R / MapAnything 估深、点云反投影、GS 优化或 PLY 导出阶段。论文中的三维重建展示不能据此解释为内部始终运行一个高斯世界。

其生成能力可以用一个接口概括：

```text
下一段 latent = 视频生成器(
    当前噪声、目标相机、文本、最近上下文、按目标相机查询的历史记忆
)
```

“3D-aware”表示记忆编码和读取利用三维相关归纳偏置及相机条件，不等于有显式、可碰撞、可测量的完整三维地图。

## 3. 沿代码走一遍实际数据流

### 3.1 输入和相机

[cli.py](../../../WorldCrafter/worldcrafter/cli.py)负责图片、提示词、相机、Base/Fast 及输出参数；[camera.py](../../../WorldCrafter/worldcrafter/camera.py)把前后左右移动、转头和回退动作转换为轨迹。

相机文件使用全局 c2w，每帧一个矩阵，支持 `[T,3,4]` / `[T,4,4]`，坐标轴为右、下、前。轨迹要求完整 **33 帧/段**。对外提供模型度量尺度的平移，内部相机表示由代码转换，不能提前重复归一化。[上游相机指南](../../../WorldCrafter/test/README.md)

相机“forward / yaw / reverse”动作控制观察者位置，不是推物体、施力或机器人操作接口。

### 3.2 首段

图片经 Wan VAE 编码，作为图像前缀；文本经文本编码器提供条件。首段没有生成历史，长期记忆使用零占位。目标相机通过专用相机条件分支进入视频模型，生成第一段。

[streaming.py](../../../WorldCrafter/worldcrafter/streaming.py)中的 Fast I2V 实现还对输入前缀做小噪声扰动；因此“首图作为条件”也不等于每个解码像素被绝对锁定。

### 3.3 历史档案与检索

每段对应 **9 个 latent 时间位置**；生成后将它们和相机关系加入历史。下一段保留最近一个 latent，再从更早历史中检索 **8 个不同位置**，形成 9 个来源视图。

核心实现在 [trajectory_memory_provider.py](../../../WorldCrafter/worldcrafter/repencoder/trajectory_memory_provider.py)：`_select_history()` 和 `render_memory()`。当前目标段取 latent 槽位 `(2,4,6,8)` 作为四个查询视角。

[trajectory_fov.py](../../../WorldCrafter/worldcrafter/repencoder/trajectory_fov.py)根据视锥采样与联合覆盖选择互补历史，而非只取末尾帧或均匀采样。这里的覆盖是相机视锥几何近似，**没有真实表面深度的遮挡判定**，不能把覆盖分数当成场景内容正确概率。

注意计数单位：这些“9 个来源”是 latent 时间位置，不是 9 张完全独立的原始 RGB 图片，更不是 9 次真实观测。

### 3.4 编码与目标相机读取

[RepEncoder.forward_conditioned](../../../WorldCrafter/worldcrafter/repencoder/model.py)的实际调用顺序为：

```text
source_latents [B,9,16,48,80]
      ↓ InputLayer：latent 特征适配
      ↓ DinoTail
      ↓ RepresentationBackbone：融合来源与相机信息
      ↓ RepFeature：用目标相机射线查询场景特征
      ↓ OutputLayer：投影到视频条件通道
memory4 [B,16,4,48,80]
```

来源相机 token 为 `[B,9,11]`，目标射线为 `[B,4,6,384,640]`。结构配置在 [config.py](../../../WorldCrafter/worldcrafter/repencoder/config.py)，当前具有严格尺寸与架构检查，不能随意改分辨率或来源数量。

论文描述编码器与读取模块由 LagerNVS 初始化并适配到视频 latent；代码中存在 DINO/VGGT 风格组件，并不表示运行时先调用完整 VGGT 输出深度。这里输出的是目标条件特征，不是目标 RGB 或 GS。

RepEncoder 将相机变换到最新来源相机的相对坐标，并根据来源基线做尺度归一化；对近零基线有专门处理。[camera.py](../../../WorldCrafter/worldcrafter/repencoder/camera.py)中归一化包含 `1.35 × 最大来源平移距离`。这是模型约定，不应移植成任意几何系统的通用尺度修正。

### 3.5 记忆进入扩散

[transformer.py](../../../WorldCrafter/worldcrafter/diffusers/transformer.py)通过 `patch_memory` 将 `memory4` 转为 token，再与最近上下文和待生成 token 拼接。相机相关注意力由 [ucpe](../../../WorldCrafter/worldcrafter/ucpe) 模块参与处理。

这里的“4 帧记忆”实际是四个 latent 特征平面，经 patch 化成为许多 token；不是只有四个向量。`patch_mid` 对较近历史作更强压缩，`patch_memory` 则单独处理查询记忆。

推理具有段级因果性：先有上一段，才能生成下一段；当前整段由扩散模型联合生成。流式输出单位是段，不能简单描述成每一张 RGB 严格独立自回归。

### 3.6 生成后保存什么

生成 latent 被追加到历史档案，最近上下文窗口更新，VAE 解码得到视频。Base 提供分段状态保存与续跑接口，Fast 当前拒绝 resume/state export。

**固定的是每次编码选取的来源数量和送进 DiT 的记忆规模，不是总历史存储。** `streaming.py` 明确执行 `generated = torch.cat([generated, latents], dim=2)`。它每段重新检索、编码历史，并非一个固定大小的全局隐状态不断原位更新。

以该代码 float32、每段 9×16×48×80 个 latent 数值估算，仅累计 latent 约 **2.11 MiB/段**，未包括模型、注意力、输出和临时张量；总显存与耗时不能据此判断。检索候选也会随历史增长。

## 4. 与现有 WorldWarp 和 F/G/H 的关键差异

| 维度 | 本地 WorldWarp 原版 | 本地 F/G/H | WorldCrafter |
|---|---|---|---|
| 长期信息入口 | 上一段生成 RGB | 生成历史，G/H 另有首图锚点 | 历史 latent 档案与相机 |
| 几何 / 记忆 | TTT3R 后重新拟合局部 GS | MapAnything；F/G 拟合 GS，H 点渲染 | 隐式场景特征与目标相机读取 |
| 给视频模型的条件 | GS 粗 RGB 与有效性掩码 | GS / 点云粗渲染条件 | 查询记忆 token＋直接相机条件 |
| 选历史依据 | 当前基线末尾连续 5 张源图 | 基准适配为均匀几何关键帧 | 最近 latent＋视锥互补覆盖历史 |
| 产物 | 视频及逐段局部 PLY | 视频，按保存策略有中间资产 | 视频、元数据、Base 可保存续跑状态 |
| 统一持久 GS | 无 | 无跨段持久 GaME 地图 | 主路径也无 |

因此它能帮助我们检验一个问题：**在同等任务中，显式估深与 GS 渲染究竟提供了必要约束，还是也引入了可避免的误差和开销？** 但不同骨干、训练数据与模型预算会混杂结果，不能把两个成片的差异全部归因于记忆形式。

## 5. 对你当前任务的价值排序

### A：优先作为独立基线

先用上游自带静态雕塑例子验证部署，再在 classroom 和本地雕像输入上设计“离开—回访”轨迹。上游 `socrates` 是另一个例子，不能把它当作我们 DL3DV 雕像场景的复现。

对照同时看目标相机误差、回访内容保持、完整序列和成本。先做静态任务，提示词应明确雕像静止。好看的动态视频不构成静态重建正确的证据。

WorldCrafter 默认 384×640、33 帧/段、16 fps；我们的 DL3DV 为 720×480、49 帧分段且重叠、225 帧。不能直接截帧后声称同协议。应先建立共同的连续相机路径、采样时间和裁剪/FOV 规则，再定义配对评分；原生展示和共同协议结果分开报告。

### B：低成本借鉴历史选择

把视锥联合覆盖选帧作为 F/G 的候选策略，与末尾选帧和均匀关键帧比较，固定数量、几何网络、目标轨迹和采样参数。选帧逻辑有机会先独立验证，而无需改变 WorldWarp 的 DiT。

但当前算法基于请求相机；若生成内容没有跟随请求，检索也可能选错。可研究引入独立几何一致性与来源风险，并测试是否真正改善后续生成，不能只报告覆盖分数增加。

### C：中长期借鉴目标驱动的记忆接口

不是先把所有历史压缩成与任务无关的向量，而是根据“接下来往哪里看”决定读出什么。可研究显式几何支持与隐式外观记忆的联合条件：可靠区由几何保持，缺失或冲突区由学习记忆补充。

这需要新条件适配与训练，WorldCrafter 的 RepEncoder 不能直接替代 WorldWarp 的粗 RGB：两者语义、token 接口和联合训练分布不同。即使 latent 通道数碰巧相同，也不意味着可互换。

### D：如果目标仍是完整 3DGS 资产

可以提出另一条待验证管线：WorldCrafter 生成多视图 → MapAnything / 多视图重建估几何 → 全局 GS 拟合。这里生成结束后的 GS 是独立重建产物，不是 WorldCrafter 内部状态。

优先测试静态场景，并先检查不同视图是否能由同一刚性场景解释；动态物体需要独立对象或动态表示。不要把请求位姿无条件当作生成帧的真实位姿，也不要把生成的多视图当成新的真实证据。

## 6. 它对研究新颖性的影响

“加入隐式三维记忆”“按目标相机查询历史”“让编码器和视频模型共同训练”都已成为直接相关工作，不能继续作为未经比较的原创主张。

仍值得验证的差异包括：

1. **来源与纠错：** 区分真实观测、生成假设及共享祖先，避免重复生成导致错误置信增长。注入可控错误后，检查新真实证据能否纠正。
2. **增量记忆：** 减少每段重复编码，同时保持回访质量。论文已明确将增量流式编码列为未来方向，因此必须提出具体实现与新结果，不能只提出概念。
3. **显式资产与隐式记忆一致性：** 输出统一 GS 后，检验其渲染能否与生成模型的任意查询保持一致；冲突时如何定位和修正。
4. **生成运动偏差反馈：** 请求相机、内容反推相机和检索相机三者不一致时，如何避免把控制错误传播为记忆错误。

以上均是待研究方案，本次没有实验证明有效。WorldCrafter 的动态生成也不等于已具有受力、质量、碰撞和因果干预的物理状态模型。

## 7. 部署和训练方面的现实边界

当前 [pyproject.toml](../../../WorldCrafter/pyproject.toml)锁定 Python 3.11、PyTorch 2.10、Diffusers 0.37、Transformers 5.3 等；推荐独立环境，不能为了安装它修改现有三套推理环境。RepEncoder 明确要求 CUDA BF16，CPU forward 不是支持的推理路径。

Base 默认 50 步、CFG 5；Fast 常规 6 步、CFG 1，三层金字塔各 2 步，T2V 首段另有 12 步安排。Fast 使用高/低噪声模型的采样切换。Base 还依赖 Fast 权重目录中的共享组件。上述均为源码配置，不是本机速度测量。

论文第 3.4 节描述从 Helios-base 初始化，分阶段适配窗口、相机条件、记忆编码及联合训练，使用 16/32 GPU 级训练配置；其报告的 Fast 16 fps 对应 4 GPU 机器，不能承诺单张 H20 同速。论文中的记忆处理加速也不是完整视频推理的等倍加速，具体见[本地论文](../../../WorldCrafter/assets/WorldCrafter.pdf)。

当前快照主要提供推理与演示代码；没有发现可直接复跑论文四阶段训练的完整训练入口、数据构建和评测套件。存在模型模块与低秩分支不等于完整微调流程已交付。交互 demo 的 README 仍标注正在调试。

## 8. 下一步建议与验收

本次已完成源码获取、架构核查和 CPU 相机测试。若后续开展部署，建议按顺序完成：独立环境和权重清单 → 官方静态示例 → 本地 classroom/雕像原生协议 → 共同轨迹配对 → 选帧或记忆消融。

验收记录至少包括：commit 与权重、输入裁剪和内参、目标轨迹、实际分段、历史选择记录、完整视频、质量失败、显存与端到端时间。新增 GPU 成片之前，不把此次分析写成“WorldCrafter 已在本机跑通”。

对当前项目的定位建议：**保留 WorldWarp 作为显式几何条件基线，增加 WorldCrafter 作为相机查询隐式记忆基线；研究重点放在二者的错误传播、证据可信度与长期纠错，而不是立即串接更多模型。**
