# WorldWarp、MapAnything、GaME：当前能做什么，能替代什么

更新：2026-09-07。对应本版 PPT 第 17–21 页，以及附录 A6、A7。

结论先说清楚：**WorldWarp 提供新视角生成能力，MapAnything 提供图像到几何的前端，GaME 提供几何到可更新 GS 场景的后端。** 三者组合能覆盖我们假设框架的主要功能，但当前本地完成的是生成项目的单独验证，以及离线几何写回子链路；它们还没有接成跨轮持续读写同一地图的完整系统。

下面区分三个层次：项目原生能力、本地已经验证的入口、用于 Atlas 假设框架时的替换设计。“可以替代”均指职责上的替换，除非另有说明，不表示无修改换库或已经完成联调。

## 1. 一页就能讲清的对照

| 项目 | 输入 | 主要输出 | 用来干什么 |
|---|---|---|---|
| WorldWarp | 一张起始图 + 相机运动设置；后续段可接上一段视频 | 新视角视频、内部局部高斯缓存及相关轨迹 / 配置 | 让相机在图片场景里“移动”，补全新暴露区域 |
| MapAnything | 一张或同一场景的多张图片；模型还支持可选几何条件 | 深度、相机参数、逐像素 pointmap；本地包装器另导出聚合点云 | 从图片恢复三维几何，为场景初始化和地图更新提供输入 |
| GaME | 带相机内参、位姿的 RGB-D；原生变化适应还使用分割掩码 | 可渲染的 3D Gaussian 场景、场景 checkpoint、重渲染图 | 增补、优化、保存场景；原生可适应重新观测时的场景变化 |

有三个容易混淆的输出：

- 视频：生成出来的一串 RGB 画面。
- Pointmap / 点云：像素或采样点对应的三维坐标，不能直接等同于训练好的高斯场景。
- GS 场景：包含高斯位置、形状、透明度、颜色等参数，可从给定相机渲染；也不自动等于 mesh、碰撞体或物理仿真世界。

## 2. WorldWarp：生成侧基线，但本来就含几何和 GS

### 2.1 它当前做的事情

WorldWarp 的方法将历史内容构造的三维约束和视频生成结合起来，按视频段继续生成。粗渲染提供结构，生成模型修补缺口并改善画面；新视频再作为下一段的历史。[官方方法页](https://hyokong.github.io/worldwarp-page/)

本地真实调用关系是：

```text
起始图 / 上一段视频
    ↓
TTT3R / CUT3R：恢复已有内容的深度与相机信息
    ↓
选择源帧，初始化并优化局部 GS
    ↓
按目标相机轨迹渲染粗 RGB 与几何有效区域
    ↓
VAE 编码 + WorldWarp 的条件视频生成模块
    ↓
新视角视频 → 下一段输入历史
```

对应本地源码：`WorldWarp/pose_control.py:1249` 的 `run_inference_chunk`；`WorldWarp/src/ttt3r/ttt3r.py:1573` 的 GS 初始化；`:1787` 的新建 `GS3DWarper`。

### 2.2 用户实际给什么

- 起点可以是一张上传图或示例图。
- 相机设置可以来自运动预设、手工位移 / 旋转，或参考视频中提取的轨迹。
- 提示文字可参与内容 / 风格控制；GUI 也有生成首图入口。该入口不应被理解为已经直接输出完整的文本到三维世界资产。
- 后续 chunk 可读取上一段视频，不要求用户每一段重新提供完整多视角数据。

单图启动时，程序可以在内部构造时序输入；**实测输出 81 帧，不等于要求用户输入 81 张独立照片。** 不同帧数配置还需满足模型 / VAE / 调度的形状约束，不能任意改一个整数就保证可用。

### 2.3 本地已经验证了什么

已完成 Conda、权重、CUDA 扩展、GUI 以及单段完整生成验证。测试为 1 chunk、81 帧、720×480、30 fps，同时生成约 5 万个高斯的 PLY 缓存。具体模型与路径见 [WorldWarp 本地部署记录](../../archive/WORLDWARP_SETUP.md)。

这证明一条“几何条件 → 新视角视频”的实际生成链已可运行；不证明所有轨迹、多 chunk 长视频或无限探索都稳定。

### 2.4 在框架里能替代什么

| 位置 | 替换判断 | 需要说明 |
|---|---|---|
| ② 条件生成 / 新视角补全 | 可作为主要本地基线 | 与 Spatia 所在位置是功能对应，不是训练机制、条件接口或性能等价 |
| ① 已有 GS → 目标视角粗图 | 内部已包含 | 当前是自己的局部 GS；外部持久地图需要条件适配 |
| 初始局部几何 / 局部 GS 构造 | 内部已包含一部分 | 不等于完整 Marble-like 多模态世界初始化 |
| ③ 几何预测 | 通过内部 TTT3R/CUT3R 支路实现 | 可考虑由 MapAnything 承接该职责，需重接数据结构 |
| ④ 跨轮持久世界融合 | 当前本地尚未实现这一目标 | 不应把“在线缓存”直接讲成所有历史 GS 永久累加 |

### 2.5 高斯缓存最重要的边界

本地每次 `batch_warp_frames_via_3dgs` 调用创建新的 warper，并初始化新的 GS 参数和优化器。新段可以利用上一段图像中的信息，所以不是“完全没有历史”；但这与恢复同一份全局 GS 地图并增量写入不同。

更重要的是：**当前 chunk 的 PLY 在生成新视频之前就已保存。** 它主要描述用来构建本段生成条件的源内容，而不是已经重建并融合本段全部新输出帧的最终场景。

因此 WorldWarp 可用来做相机控制生成基线，但还不能直接当作：

- 已接好的永久全局资产库、完整 SLAM 跟踪与回环系统；
- 支持任意外部 GS 直接作为 GUI 输入的标准接口；
- 可按任意相机和任意时间查询的连续 4D 场景；
- 与 Atlas 官方统一模型等价的完整复刻。

## 3. MapAnything：几何前端，不是 GS 生成器

### 3.1 它的原生能力

模型接受一张或多张图，也可以结合标定、相机位姿、深度等几何输入，预测场景几何与相机信息，覆盖多个重建任务。[官方项目页](https://map-anything.github.io/)

本地 [README](../../../../MapAnything/README.md) 给出了 image-only 与 multimodal 两类接口。我们已安装的包装器采用 image-only 路径：

```text
RGB 图片 / 图片目录
    ↓
MapAnything 联合几何推理
    ├─ 每帧 z-depth
    ├─ 每像素三维 pointmap
    ├─ 相机 K 和 OpenCV c2w
    └─ 有效性与置信度
    ↓
本地包装器：NPZ 导出 + 同批次点云体素聚合
```

### 3.2 当前本地能接什么、输出什么

入口：[run_mapanything.sh](../../../../run_mapanything.sh)，实际执行 [scripts/infer_geometry.py](../../../../scripts/infer_geometry.py)。

可接真实观测图、WorldWarp 生成帧、GS 渲染图。`--source-kind` 用于记录来源，不会自动把生成图变成真实观测，也不会自动增强预测精度。

| 文件 | 内容 | 下游用途 |
|---|---|---|
| `posed_rgbd.npz` | RGB、z-depth、valid、K、c2w、confidence | 当前 GaME 适配器的直接输入 |
| `pointmaps.npz` | 每像素世界坐标点及有效掩码 | 点图检查、几何对齐、过滤、后续融合 |
| `pointcloud_fused.ply` | 当前推理批次共享坐标内的体素聚合点云 | 可视化与几何初值，不是长期 SLAM 图 |
| `report.json` | 来源、帧数、有效点、耗时和显存等 | 可追溯与验收 |

原模型支持已知相机和深度作为条件，但**当前本地 CLI 还没有这些参数入口**。下一步可以暴露条件输入，或结合重叠区域做后对齐，不能把现有 RGB 包装器当成已固定全局相机的版本。

### 3.3 本地已验证什么

默认与 Apache 两种权重均已安装并测试。三帧既有 WorldWarp 图像得到 84,245 个聚合点；另一次以 GS 渲染图作输入的测试也通过。来源见 [几何部署与验证记录](../../archive/GEOMETRY_SETUP.md)。

这些数字证明输入来源与输出接口跑通，不构成几何精度保证。模型预测的尺度尚未通过真实标定核验。

### 3.4 它能替代的职责

- 框架里的 **③ 图像到几何重建**：直接对应。
- WorldWarp 内部 TTT3R/CUT3R 的几何预测职责：可替换候选，但需适配输入多帧组织、返回字段、位姿与尺度；并不继承原时序模型的全部状态机制。
- 单目深度、多视角几何预测、部分相机初始化任务：可作为一体化前端或对照方案。
- 传统 SfM/MVS 后续 GS 训练所需的几何初值：上游有 COLMAP 格式导出与 gsplat 训练衔接，不意味着取代整个 COLMAP 工具链、特征轨迹、BA 或长序列回环流程。依据是 [本地上游 README 的 COLMAP 与 GSplat 章节](../../../../MapAnything/README.md)。

### 3.5 它不能直接替代什么

- 不负责“粗图补出新视角”的 RGB 视频生成。
- 模型本身不直接输出已优化的场景 GS。接后续 GS 训练或 GaME，才会获得 GS 场景。
- 不直接维护跨独立推理调用的长期地图，也不自动做全局回环。
- 静态场景的多图联合重建不能直接当成完整动态 4D 建模。

所谓 `pointcloud_fused.ply` 的“融合”，当前具体含义是**同批次共享坐标下的体素聚合**。独立调用的坐标原点、尺度与位姿不可默认完全一致，不能把两次 PLY 简单相加就声称世界扩大了。

## 4. GaME：地图后端，需已有几何与相机输入

### 4.1 它的原生能力

GaME 以带位姿的 RGB-D 观测建立高斯地图，并处理重新观测时出现的场景变化，例如新物体加入、旧物体被移走。其方法包括关键帧管理、变化适应、旧区域处理和局部多帧优化。[官方方法页](https://vladimiryugay.github.io/game/)

本地核心路径：

```text
RGB-D + K + 位姿 + 掩码
    ↓
关键帧选择
    ↓
增补高斯 / 新旧几何处理
    ↓
单帧与多帧优化
    ↓
GS 场景 → 渲染 / PLY / 场景 checkpoint
```

### 4.2 当前本地的实际输入

入口：[run_game.sh](../../../../run_game.sh)，实际执行 [scripts/fuse_geometry_game.py](../../../../scripts/fuse_geometry_game.py)。它读取 MapAnything 导出的 `posed_rgbd.npz`，然后构造 GaME 数据帧。

必须保持：

- RGB 与 depth 对应同一帧、同一处理分辨率。
- K 跟随图像缩放，并保留主点信息。
- 中间格式用 OpenCV c2w；进入 GaME 实际接口时求逆得到 w2c。
- 无效深度不参与有效几何。
- 当前包装器使用一个全图静态 mask；这不是 SAM 分割，也不是自动运动识别。

所以“GaME 输入带位姿 RGB-D”作为直观介绍是对的；实施时还要补上 **K 与掩码约定**。

### 4.3 当前输出与验证

- `gaussians.ply`：当前场景的高斯资产，可用于兼容渲染器。
- `checkpoints/checkpoint.pth`：当前场景状态，不是通用预训练 RGB → GS 权重。
- `configs.json`：运行配置。
- `render_*.png`：输入相机上的重渲染检查。
- `report.json`：输入帧、关键帧、高斯数、种子增补、重载检查等。

三帧 WorldWarp 图像经 MapAnything 后输入 GaME，得到 18,991 个高斯；场景保存、重载与渲染均已验证。测试用低分辨率、少量额外迭代，属于安装验收。

同一次调用内，后续关键帧确实向该场景增补和优化高斯，不是三个完全独立场景。但下次调用现有包装器仍创建新的 GaME 实例，并未恢复之前地图继续训练。

### 4.4 它能替代什么

| 目标功能 | 能否承担 | 当前还要做什么 |
|---|---|---|
| ④ RGB-D → GS 增补、优化、保存 | 核心职责，可用 | 校准输入几何质量与迭代设置 |
| 单图 / 多图几何到初始局部 GS | 可与 MapAnything 组合承担 | 只针对输入覆盖或先验推断的局部区域，不等于完整生成世界 |
| WorldWarp 局部 GS 优化器的地图职责 | 可作为替换方案 | 接入相机、mask、渲染条件，并明确旁路原局部建图逻辑 |
| GS → RGB / alpha 等渲染 | 原生已有 | 若接统一 gsplat 接口，要适配高斯参数与相机；不能假定已完成替换 |
| 跨轮持久地图 | 有原生恢复基础 | 本地 CLI 续训 / 历史管理 / 坐标锚 / 门控尚待开发 |
| 重新观测时场景变化适应 | 原生方法覆盖 | 当前全图静态 mask 与三帧测试未覆盖完整变化场景 |

### 4.5 原生恢复、本地重载、跨轮续图，不是同一个概念

原生 `GaME` 类支持 `checkpoint_path` 和 `all_train_data`。恢复时不仅读高斯参数，还需通过历史数据重建关键帧等信息。相关源码位于 `GaME/src/entities/game.py:20`、`:647`、`:672`。

本地现状分三层：

1. 原生接口具备恢复基础。
2. 已验证保存的场景能重新加载，且高斯数量一致。
3. **尚未实现包装器的跨调用恢复 → 接收新数据 → 再训练 → 再保存流程。**

因此不能说“GaME 完全不支持恢复”，也不能说“现在反复调用 run_game.sh 就会自动续图”。

### 4.6 哪些不能靠它替代

- **不是 RGB-D 预测器。** 没有深度和位姿时，先用 MapAnything 等前端或传感器提供。
- **不是完整相机跟踪和回环系统。** 当前 `train()` 直接将输入 pose 放入 `estimated_poses`，源码还标记跟踪模块是后续工作。
- **不是任意点云 PLY 的通用合并工具。** 本地入口需要 RGB-D、相机等信息；仅有 pointmap 时要补足或转换数据。
- **不是连续 4DGS。** 适应物体增删、位置变化，不等于保留可查询的完整连续时间动态资产，也不等于预测未来运动。
- **不是未知空间的内容生成器。** 没有真实观测或生成候选，地图后端不会凭空给你新的可信房间。

另一个测试边界：当前原生 `detect_additions` 在已有关键帧数大于 2 时才运行，即通常从第 4 个被接受关键帧开始。前三帧仍会增补 GS、优化和执行其他处理；只是不能用三帧安装测试覆盖全部变化检测分支。

## 5. 合并后，具体替换哪一段

### 5.1 对 WorldWarp 内部的替换

```text
原 WorldWarp 的几何条件支路：
历史帧 → TTT3R/CUT3R → 局部 GS 优化 / 渲染 → WorldWarp 生成模块

目标组合：
历史帧 + 新帧 → MapAnything → GaME 持久地图 / 渲染适配 → WorldWarp 生成模块
```

**保留生成器，替换并扩展几何侧**，是最准确的说法。

MapAnything 不替代 WorldWarp 的 Wan 生成模块；GaME 也不替代视频生成。两者一起承担几何预测、场景表达与更新，但要避免 WorldWarp 内部再启动一套互不一致的局部坐标系统。

### 5.2 对我们 Atlas 假设框架的覆盖

| 功能 | 最合适的现有角色 | 当前覆盖程度 |
|---|---|---|
| 文本 / 单图 / 多图入口 | 上层入口组织；WorldWarp 有首图路径 | 单图基线可用，多模态统一初始化不完整 |
| 初始已覆盖区域的 GS | MapAnything + GaME，或 WorldWarp 内部局部建图 | 可做局部初始资产，不是完整 Marble 能力替身 |
| ① 从已有世界渲染条件 | WorldWarp 内部渲染、GaME 渲染器或 gsplat 适配 | 渲染能力已有；跨项目格式与全局地图接口待接 |
| ② 补出新视角内容 | WorldWarp | 独立项目可用，持久 GaME 条件接入待做 |
| ③ 新图恢复几何 | MapAnything | 本地 RGB 推理与导出已跑通 |
| ④ 融合、优化、保存地图 | GaME | 单次多帧融合已跑通，跨轮状态恢复待接 |
| 首帧 / 历史参考管理 | WorldWarp 历史机制 + 新的调度层 | 长期关键帧、世界坐标绑定与筛选仍需实现 |
| 完整静态世界闭环 | 三者 + 适配与调度层 | 未完成联调 |
| 连续 4D 世界 | 需要动态生成与动态重建 / 表示模块 | 不在当前静态适配验证范围 |

### 5.3 开发时必须接好的四件事

1. **生成条件适配。** 将持久地图按目标相机渲染成 WorldWarp 需要的 RGB 与几何有效区域，匹配分辨率、mask 语义、VAE 编码和噪声调度。
2. **世界坐标对齐。** 新帧与重叠历史联合重建，利用已知相机条件或后对齐，统一尺度、c2w / w2c 和深度定义。
3. **场景状态延续。** 恢复同一个 GaME 场景及其必要历史，不重复创建互相独立的地图。
4. **候选质量门控。** 检查重投影、可见性和置信度，保护旧区域；错误生成可以拒绝写入并回退。

只把已有 GS 渲染图反复输入 MapAnything + GaME，证明的是重渲染与重建接口可以走通，**并没有新增真实观测信息**。几何预测器可能依靠先验修整结果，但也可能积累误差。要扩展未见区域，新内容须来自生成器或新的真实观测；自洽不自动等于真实。

## 6. 输入帧数与长期运行

| 项目 | 当前本地设置 | 正确理解 |
|---|---|---|
| WorldWarp | 单图启动，实测 81 帧单 chunk | 输出按段组织，不代表输入必须有 81 张图；未证明无限多段稳定 |
| MapAnything | 至少 1 张；CLI 默认最多取 8 张 | 8 是包装器截断参数，不是模型固定上限；更长输入受显存和实现限制 |
| GaME | CLI 默认最多取 3 帧，再选关键帧 | 3 不是建图硬限制；要匹配前端帧数，同时处理资源与状态增长 |

例如让两步都处理 8 帧，应分别设置两个脚本的 `--max-views 8`；只改 MapAnything 不改 GaME，后端仍默认只处理前 3 帧。这是参数对齐建议，不是已完成的 8 帧新测试。

对于“无限帧”，合理工程目标是**有界资源下持续处理新的帧**：滑动窗口、选关键帧、地图分区 / 预算、全局坐标与恢复机制共同作用；不是把无限多帧塞进一次模型前向。当前包装器尚不提供这样的无限流入口。

## 7. 最小下一步与验收

建议先固定场景时间、只做小相机移动：

1. 从当前图像得到初始 GS，并保存地图版本 0。
2. 用该 GS 渲染目标视角条件，接 WorldWarp 生成新帧。
3. 将可信新帧与少量重叠历史送入 MapAnything，并对齐旧世界。
4. 恢复同一 GaME 地图，接受通过检查的新区域，得到版本 1。
5. 第二轮必须渲染版本 1；检查第一轮新增区域是否真的成为约束。
6. 返回起始相机，检查旧区域有没有被改坏。

通过这些条件后，再扩大探索距离、输入帧数、历史长度和动态复杂度。当前最有价值的里程碑是 **两轮共享同一世界**，而不是一次导出更多彼此独立的 PLY。
